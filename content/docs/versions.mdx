The v2 builds are reproducible: the protocol repository records the expected hash of each
release build in
[`scripts/release-hashes.txt`](https://github.com/lazor-kit/lazorkit-protocol/blob/develop/scripts/release-hashes.txt),

To check a program yourself, dump it and hash the number of bytes in the table (the
program account can be larger than the program it holds; the rest is zeros):

```bash
solana program dump 57bTNWqtYTJbWuLWASKo6GqUTAK6oFDUR5c6hEc6V8nv v2-devnet.so --url devnet
head -c 158096 v2-devnet.so | shasum -a 256

```

### Layout revision 2

From build `e7930c8b…` every authority and session the program creates records the
account that paid its rent (account layout revision 2). `RevokeSession`,
`CloseExpiredSession`, `RemoveAuthority` and `TransferOwnership` refund that rent only to
the recorded payer; any other destination is refused with `RefundDestinationMismatch`
(3039), whoever signs or pays for the close. `CloseExpiredSession` is still open to anyone,
but the rent goes to the recorded payer, not to the caller. On a sponsored flow the payer
is the relayer's fee payer.

- **Older accounts keep the old rule.** Authorities and sessions written before revision 2
  (on devnet, those created before 2026-10-13) and v1 accounts record no payer: their rent
  goes to the destination the instruction names.
- **SDKs.** `@lazorkit/sdk-legacy` 2.1.0 and `@lazorkit/sdk` 1.0.0-rc.8 read both revisions
  and default the refund to the recorded payer. Earlier releases build every instruction
  the same way and default the refund to the transaction's `payer`, which is right when the
  same payer created the account (a relayer closing what it sponsored). They do not know
  revision 2: they read a revision-2 Delegate's policy and a session's actions 32 bytes
  early, and the approval decoders of sdk-legacy 2.0.0 return `null` for revision-2
  accounts. The portal code for the coming update
  ([`lazor-kit/portal-v2`](https://github.com/lazor-kit/portal-v2)) reads both revisions.
- **Rent.** Each authority and session is 32 bytes larger: 162,560 lamports more rent at
  the devnet and mainnet rate on 2026-10-14 (5,080 lamports per byte), returned on close.

## Audit status

**Protocol v2** (`57bTNW…`, `LazorFroi…`): **not externally audited.**

- A prior external audit by Accretion for the Solana Foundation (report A26SFR1, February
  2026, in the repository's [`audits/`](https://github.com/lazor-kit/lazorkit-protocol/tree/main/audits)
  folder) covered only the predecessor codebase, `lazor-kit/program-v2` at commit
  `cd09588d`, from which `lazor-kit/lazorkit-protocol` was forked. It did not cover the
  current programs' code: the changes made since (the protocol fee layer, ranks and
  policies, multiple Owners, `MigrateWallet`, session time in seconds, rent refunds to the
  recorded payer, and others) were never externally audited.
- Internal reviews: independent reviewers, each working from a fresh context on one
  subsystem; every issue found was reproduced with a test before it was fixed. The scope,
  method and results are public in
  [`docs/audit/`](https://github.com/lazor-kit/lazorkit-protocol/tree/main/docs/audit).
- Tests: on the current source (`develop` at `345625b`, the last change to the program and
  the SDKs), CI runs 512 Rust tests (236 unit tests, and 276 integration tests that load
  the built program, the sunset build included) and 361 tests of `@lazorkit/sdk`, all
  passing.
- Reproducible builds: see [Full build hashes](#full-build-hashes).
- Two-id rehearsal: the whole rollout (v2 at its new id, v1 upgraded to the sunset build,
  v1 wallets migrated by owner key and by passkey) was run end to end on a local validator
  at both the mainnet and the devnet ids, 18 of 18 checks each, and the rollback at the
  mainnet ids (2026-10-04, on an earlier build). The deploy checklist repeats it with the
  final release builds before the mainnet deploy.

**Protocol v1** (`LazorjRF…`, `4h3XoNRe…`): **not externally audited.** It is also forked
from `lazor-kit/program-v2`, with changes that include the protocol fee layer; the prior
audit did not cover them. It was reviewed internally before its mainnet deploy
([2026-04-21](https://github.com/lazor-kit/lazorkit-protocol/blob/main/docs/security-review-2026-04-21.md),
[2026-04-28](https://github.com/lazor-kit/lazorkit-protocol/blob/main/docs/audit-2026-04-28/findings.md)).

### Tested: web SDK × portal × program

`@lazorkit/wallet` 3.3.0, 3.4.1 and 4.0.0-next.0, run on 2026-10-12 against the portal code
for the coming update (`lazor-kit/portal-v2` at `e9bd0ca`) and both devnet programs, with
devnet's v2 on build `f2779b66…`, before the 2026-10-13 upgrade; this matrix has not been
re-run on `e7930c8b…`. A script drove each step in Chromium with a virtual passkey and
approved every portal screen the way a user would; every transaction that landed was read
back from devnet.

**v2 on devnet** (`57bTNW…`, build `f2779b66…`):

| SDK | Connect | Send | `signMessage` | `createSession` | Add / remove a key |
| --- | ------- | ---- | ------------- | --------------- | ------------------ |
| `@lazorkit/wallet` 3.3.0 | ✓ | ✓ | refused by the portal¹ | **fails with 3008**² | ✓, generic confirmation³ |
| `@lazorkit/wallet` 3.4.1 | ✓ | ✓ | ✓ | **fails with 3008**² | ✓, generic confirmation³ |
| `@lazorkit/wallet` 4.0.0-next.0 | ✓ | ✓ | ✓ | ✓, the portal shows the session's limits | ✓; adding: generic confirmation³, removing: shown in full |

**v1 on devnet** (`4h3XoNRe…`), with a paymaster that sponsors v1 set as
`v1PaymasterConfig` (LazorKit's default devnet paymaster sponsors v2 only):

| SDK | Connect | Send | `signMessage` | `createSession` | Add / remove a key |
| --- | ------- | ---- | ------------- | --------------- | ------------------ |
| `@lazorkit/wallet` 3.3.0 | ✓⁴ | ✓ | refused by the portal¹ | ✓, generic confirmation³ | ✓, generic confirmation³ |
| `@lazorkit/wallet` 3.4.1 | ✓ | ✓ | ✓ | ✓, generic confirmation³ | ✓, generic confirmation³ |
| `@lazorkit/wallet` 4.0.0-next.0 | ✓ | ✓ | ✓ | ✓, generic confirmation³ | ✓, generic confirmation³ |

1. Releases before 3.3.1 send messages in a format the updated portal does not sign. The
   app's `signMessage` rejects with `Request not readable: The data to sign is not valid
   base64.` See [Upcoming changes](/upgrade-notice).
2. 3.x sends the session's expiry as a slot; v2 reads it as Unix seconds and refuses it
   (`InvalidSessionDuration`, 3008). With 3.4.1 and earlier this happens after the user has
   approved with their passkey.
3. The portal shows "a change LazorKit can't show", which the user must approve
   explicitly. Only 4.0 sends `createSession`, `revokeSession` and `removeAuthority` in a
   form the portal can show in full, and only for v2 wallets.
4. A returning v1 user sees one extra generic confirmation at sign-in with 3.3.0.

Not covered by this run: `@lazorkit/wallet-mobile-adapter` (2.4.0 and 3.0.0-next.0 were not
tested here), mainnet, `@lazorkit/sdk-legacy` other than the 1.4.0 / 2.0.0 that the wallet
releases installed, and Safari or platform authenticators.

**On build `e7930c8b…`** (2026-10-13), `@lazorkit/wallet` 4.0.0-next.1 with
`@lazorkit/sdk-legacy` 2.1.0 passed the protocol repository's devnet smoke run, through the
portal code at `lazor-kit/portal-v2` `7d7ed95` and LazorKit's devnet relayer: the portal
showed a new session's limits, the session was spent, a payment over its per-payment cap
was refused (3023), SOL from a token-only session was refused (3037), and a
`revokeSession` refunded the session's rent to the relayer's fee payer. New passkey
authorities and sessions were written at layout revision 2. The 3.3.0 and 3.4.1 rows above
were not re-run on this build.

<Callout type="warn" title="Creating sessions on v2 needs 4.0">
  Creating a session on a v2 wallet requires `@lazorkit/wallet` 4.0 or
  `@lazorkit/wallet-mobile-adapter` 3.0 (pre-releases on the npm `next` tag). This holds on
  devnet today and on mainnet once v2 is deployed there, since the planned mainnet build
  has the same session time rules. The coming `@lazorkit/wallet` 3.4.2 refuses
  `createSession` on a v2 wallet with a clear error before the passkey prompt. See
  [Migrating to 4.0](/react-sdk/migrating-to-4).
</Callout>
