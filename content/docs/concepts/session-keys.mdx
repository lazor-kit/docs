---
title: Session Keys
description: Scoped, time-bound delegation keys — action types, spending limits, deferred execution, and revocation.
---

A session key is an ephemeral Ed25519 keypair with an expiry slot and a list of action
constraints. It lets an app or agent execute on behalf of a wallet **without a passkey
prompt per transaction**.

<Callout type="info" title="When to use session keys">
  Session keys are for **delegation** — giving an app or agent scoped permission to act on
  the user's behalf. You don't need one for direct user execution: a passkey owner can
  always sign a transaction themselves.

  Reach for a session key when:
  - An agent / bot executes on a schedule without the user present
  - An app wants to batch or automate actions without prompting every time
  - You need to constrain *what* an executor can do (which programs, what value, until when)

  A key that should keep its limits for good, with no expiry, is a **Delegate** authority
  instead; see [Ranks & policies](/concepts/rbac).
</Callout>

## Mental model

```
1. Owner/Admin creates a Session PDA with a fresh Ed25519 public key + action list
2. The session's secret key is kept by whoever will sign with it (see below)
3. The holder signs Execute with the session key — no passkey prompt
4. The program enforces the action list on every inner instruction
5. At the expiry slot the session stops signing; its account can then be closed
```

**Who keeps the key:**

- **React SDK** (`@lazorkit/wallet`): `createSession` generates the keypair and keeps the
  secret key in `localStorage['lazorkit-session']`, as plain text, for
  `signAndSendWithSession`. Pass `sessionKey` (a public key) to register a key your
  backend holds instead; it is never stored.
- **React Native SDK and the contract SDKs:** you generate the keypair and keep the secret
  key yourself, in secure storage (`expo-secure-store`, a KMS, a backend vault). Keep the
  wallet it belongs to with it, use it only while that wallet is connected, and delete it
  at disconnect and once its session is revoked or expired.

<Callout type="info" title="Next release (3.3.0)">
  Not published yet. `@lazorkit/wallet` 3.3.0 keeps the session key as a
  non-extractable WebCrypto key in IndexedDB (a sealed seed where the browser has no
  WebCrypto Ed25519, the page's memory without IndexedDB), not as plaintext in
  localStorage. It binds the key to the wallet that created the session: the key signs
  only while that wallet is connected, and `KeyWalletMismatchError` is thrown otherwise.
  `disconnect()` deletes the key (also one whose session lands after it) unless you pass
  `disconnect({ keepSessionKeys: true })`, a key whose session has expired is deleted
  when it is next read, and `forgetStoredKeys()` deletes every key the SDK keeps.
</Callout>

Sessions are the **cheapest** execution path: no Secp256r1 precompile runs. Measured in
April 2026 on protocol v1, a session `Execute` took about 4,105 CU against about 9,495 CU
for a passkey `Execute`; v2 adds a hash input and runs the policy engine, and has not been
re-measured.

## Creating a session

Every SDK refuses to create a session with **no actions** unless you pass
`unrestricted: true`: such a session can spend the whole vault through any program until
it expires. (Since `@lazorkit/wallet` 3.0.0, `@lazorkit/wallet-mobile-adapter` 2.0.0 and
`@lazorkit/sdk-legacy` 1.0.0.)

### From the React Native hook

The RN SDK takes the raw `SessionAction[]` catalogue:

```ts
import { Actions, useWallet } from '@lazorkit/wallet-mobile-adapter';
import { Keypair } from '@solana/web3.js';

const sessionKp = Keypair.generate();
const currentSlot = BigInt(await connection.getSlot());

const { sessionPda } = await createSession(
  {
    sessionKey: sessionKp.publicKey,
    expiresAtSlot: currentSlot + 216_000n,   // ~24h at 400 ms a slot
    actions: [
      Actions.solRecurringLimit({ limit: 1_000_000_000n, window: 216_000n }),
      Actions.solMaxPerTx(500_000_000n),
      Actions.programWhitelist(JUPITER_PROGRAM_ID),
    ],
  },
  { redirectUrl: 'myapp://cb' },
);
```

Persist `sessionKp.secretKey` in secure storage along with `sessionPda`.

### From the React hook

The React SDK takes a higher-level `SpendingLimits` wrapper for SOL limits:

```ts
const { sessionPda, sessionPublicKey } = await createSession({
  expiresInSlots: 216_000n,                 // ~24h; default 50,000 slots
  spendingLimits: {
    solLifetimeCap: 5_000_000_000n,         // 5 SOL total
    solPerTxMax: 500_000_000n,              // 0.5 SOL per tx
    solRecurring: {
      limit: 1_000_000_000n,                // 1 SOL per window
      windowSlots: 216_000n,                // 24h window
    },
  },
});
```

The React hook covers SOL limits only. For token caps or program filters, build the
session with `LazorKitClient` from `@lazorkit/sdk-legacy` and the `Actions` catalogue
(below): with an Ed25519 admin key, or with `prepareCreateSession` and a passkey
assertion you collect yourself.

### From the low-level SDK

```ts
import { Connection, Keypair, SystemProgram } from '@solana/web3.js';
import { Actions, LazorKitClient, PROGRAM_ID_DEVNET, ed25519 } from '@lazorkit/sdk-legacy';

const connection = new Connection('https://api.devnet.solana.com', 'confirmed');
const client = new LazorKitClient(connection, PROGRAM_ID_DEVNET);
const sessionKp = Keypair.generate();
const currentSlot = BigInt(await connection.getSlot());

// Ed25519 admin signs immediately:
const { instructions, sessionPda } = await client.createSession({
  payer: payer.publicKey,
  walletPda,
  adminSigner: ed25519(ownerKp.publicKey),
  sessionKey: sessionKp.publicKey,
  expiresAt: currentSlot + 216_000n,
  actions: [Actions.programWhitelist(SystemProgram.programId), Actions.solMaxPerTx(1_000_000_000n)],
});
```

For Secp256r1 (passkey) admins, use `prepareCreateSession` / `finalizeCreateSession` —
see [web3.js v1 › Session Keys](/web3js-v1/session-keys).

<Callout type="warn" title="Actions are immutable">
  Once a session is created, its action list can't be modified. To change limits, revoke
  the session and create a new one.
</Callout>

## Actions reference

Actions constrain what a session key — or a Delegate authority, whose policy is the same
kind of list — can do. The program checks them around every inner instruction during
`Execute`. **Max 16 actions**, up to 2048 bytes.

| Action                   | Enforces                                                                    |
| ------------------------ | --------------------------------------------------------------------------- |
| `SolLimit`               | Lifetime SOL cap — decrements until exhausted.                              |
| `SolRecurringLimit`      | SOL cap per window (e.g. 1 SOL/day). Resets each window.                    |
| `SolMaxPerTx`            | Max SOL gross outflow per execute.                                          |
| `TokenLimit`             | Lifetime token cap per mint.                                                |
| `TokenRecurringLimit`    | Token cap per window per mint.                                              |
| `TokenMaxPerTx`          | Max tokens per execute per mint.                                            |
| `ProgramWhitelist`       | Session can only call this program (repeatable).                            |
| `ProgramBlacklist`       | Session cannot call this program (repeatable).                              |

<Callout type="info" title="Gross outflow tracking">
  `SolMaxPerTx` uses **per-CPI lamport snapshotting**, not net flow. A DeFi round-trip
  (swap out + swap back) can't bypass the cap by ending at the same balance.
</Callout>

<Callout type="warn" title="A list bounds only what it names">
  A whitelist with no `SolLimit` leaves SOL uncapped; a SOL cap leaves tokens uncapped.
  Write a value cap for every asset the key can reach. Whatever the actions, the program
  also refuses an inner instruction that reassigns the vault or changes a vault token
  account's owner, delegate or close authority (3030–3032).
</Callout>

### Builder helpers

```ts
import { Actions } from '@lazorkit/wallet-mobile-adapter';
// or '@lazorkit/wallet' / '@lazorkit/sdk-legacy'
import type { PublicKey } from '@solana/web3.js';

declare const lamports: bigint, limit: bigint, window: bigint, mint: PublicKey, programId: PublicKey;

Actions.solLimit(lamports);
Actions.solRecurringLimit({ limit, window });
Actions.solMaxPerTx(lamports);

Actions.tokenLimit({ mint, remaining: limit });
Actions.tokenRecurringLimit({ mint, limit, window });
Actions.tokenMaxPerTx({ mint, max: limit });

Actions.programWhitelist(programId);
Actions.programBlacklist(programId);
```

Every builder also takes an optional `expiresAt` slot for that action alone.

### Expired action behaviour

Actions have their own `expiresAt` independent of session expiry.

| Action type                 | On expiry                                                  |
| --------------------------- | ---------------------------------------------------------- |
| Spending limits (SOL/token) | Treated as **fully exhausted** — any spend rejected.        |
| `ProgramWhitelist`          | **Hard deny** — all programs blocked.                      |
| `ProgramBlacklist`          | **Silently dropped** — ban lifted.                         |

## Common session patterns

### Unrestricted session (no limits)

```ts
await createSession(
  {
    sessionKey: sessionKp.publicKey,
    expiresAtSlot: currentSlot + 9_000n,     // ~1 hour at 400 ms a slot
    unrestricted: true,                      // required: no actions means no limits
  },
  { redirectUrl: 'myapp://cb' },
);
```

An unrestricted session can do anything the wallet can until it expires. Use one only
for a key you hold as carefully as the wallet itself.

### Jupiter-only swapper

```ts
await createSession(
  {
    sessionKey: sessionKp.publicKey,
    expiresAtSlot: currentSlot + 216_000n,
    actions: [
      Actions.programWhitelist(JUPITER_V6_PROGRAM_ID),
      Actions.programWhitelist(TOKEN_PROGRAM_ID),  // SPL transfers for ATAs
      Actions.solMaxPerTx(1_000_000_000n),
    ],
  },
  { redirectUrl: 'myapp://cb' },
);
```

### Usage-capped session (1 SOL per day)

```ts
await createSession(
  {
    sessionKey: sessionKp.publicKey,
    expiresAtSlot: currentSlot + 1_512_000n, // ~7 days at 400 ms a slot
    actions: [
      Actions.solRecurringLimit({ limit: 1_000_000_000n, window: 216_000n }),
    ],
  },
  { redirectUrl: 'myapp://cb' },
);
```

### Stablecoin-only spender

```ts
await createSession(
  {
    sessionKey: sessionKp.publicKey,
    expiresAtSlot: currentSlot + 216_000n,
    actions: [
      Actions.tokenLimit({ mint: USDC_MINT, remaining: 100_000_000n }),     // 100 USDC
      Actions.tokenMaxPerTx({ mint: USDC_MINT, max: 10_000_000n }),         // 10 USDC per tx
      Actions.programBlacklist(SUSPICIOUS_PROGRAM_ID),
      // SOL and other tokens are not capped by this list: add caps for them too.
    ],
  },
  { redirectUrl: 'myapp://cb' },
);
```

The program caps sessions at 6,480,000 slots (about 30 days at 400 ms) from creation
(`InvalidSessionDuration`, 3008).

## Executing with a session

### React Native

```ts
const sig = await signAndSendWithSession({
  sessionKeypair: sessionKp,
  sessionPda,
  instructions: [ix],
});
```

No passkey prompt. The Ed25519 keypair signs at transaction level.

### React

```ts
const sig = await signAndSendWithSession({ instructions: [ix] });
```

The SDK signs with the session key it stored during `createSession`. There is one slot:
a new `createSession` replaces the stored key, `revokeSession()` removes it, and in 3.2.1
`disconnect` does **not** — the key stays usable within its limits until it expires or is
revoked, connected wallet or not. On a shared device, revoke sessions when the user signs
out. The next release (3.3.0) changes this: see [Mental model](#mental-model).

### Low-level

```ts
import { session } from '@lazorkit/sdk-legacy';

const { instructions } = await client.transferSol({
  payer: payer.publicKey,
  walletPda,
  signer: session(sessionPda, sessionKp.publicKey),
  recipient,
  lamports: 500_000_000n,
});
```

## Deferred execution

For payloads too big to fit in a single Secp256r1 Execute transaction, LazorKit provides a
2-transaction deferred flow. A passkey Execute leaves only about 345 bytes for inner
instructions (see [Trade-offs](#trade-offs)), so in practice a Jupiter swap needs it: a
single-hop SOL→USDC route, with Jupiter's lookup tables and compute-budget instructions, came
to 1245 bytes through the portal in an iframe, and to 1207 through a browser tab, which
Chrome's `clientDataJSON` padding pushes over the limit.

<Mermaid chart={`

    participant C as Client
    participant P as LazorKit
    participant S as Solana

    Note over C: Compute instruction + account hashes
    C->>P: TX1 Authorize(hashes, expiry)
    Note over P: Verify Secp256r1 signature
    Note over P: Increment odometer counter
    P->>S: Create DeferredExec PDA

    Note over C: Send original instructions
    C->>P: TX2 ExecuteDeferred(instructions)
    P->>P: Verify hashes match
    P->>S: Execute via CPI
    P->>S: Close DeferredExec PDA
    Note over S: Rent refunded to the TX1 payer
`} />

### From the SDKs

The React and React Native SDKs wrap both transactions into a single method that takes
one passkey prompt:

```ts
// React Native
const sig = await authorizeAndExecute(
  { instructions: jupiterSwapIxs },
  { redirectUrl: 'myapp://cb' },
);
```

```ts
// React
const sig = await authorizeAndExecute({ instructions: jupiterSwapIxs });
```

### The window

TX2 is accepted for `expiryOffset` slots after the slot TX1 landed in: **10 to 9000**.
The React and React Native SDKs default to **1500** (since 3.2.0 / 2.2.0);
`@lazorkit/sdk-legacy`'s `prepareAuthorize` defaults to **300**. A slot's length depends on
the cluster and its load, so 9000 slots is tens of minutes, not hours.

- Past the window, TX2 fails with `DeferredAuthorizationExpired` (3014); the UI SDKs report
  it as `DeferredExpiredError`. The approval is spent.
- Until the window ends, the authorization **stays executable**, and nothing can cancel it:
  anyone holding the payload can send TX2.
- An expired `DeferredExec` keeps its rent until the TX1 payer closes it with
  `ReclaimDeferred`; only that payer can, and only after the window.

### Trade-offs

| Metric                        | Immediate Execute | Deferred (2 txs)          |
| ----------------------------- | ----------------- | ------------------------- |
| Inner instruction capacity¹   | ~345 bytes        | ~825 bytes in TX2 (~2.4×) |
| Total CU²                     | ~9,495            | ~15,667                   |
| Tx fee                        | 0.000005 SOL      | 0.00001 SOL               |
| Temp rent (refunded to payer) | —                 | 0.002116 SOL              |

¹ Room left under Solana's 1232-byte transaction limit once the transaction's own overhead
is in: v0, no address lookup table, no ComputeBudget instruction, the portal's
`clientDataJSON` in an iframe (about 40 bytes shorter from a browser tab or popup, which
leaves about 380). An empty passkey Execute is about 887 bytes; a compute-unit limit costs
about 40 more and Chrome's padded `clientDataJSON` 109 more, so under 200 bytes are left with
both. TX1 carries only hashes; an empty `ExecuteDeferred` (TX2) is about 406 bytes. TX2 is
still one transaction, though: with Jupiter's compute-budget instructions, a three-hop route
came to 1846 bytes there without Jupiter's lookup tables and 1111 with them, and a five-leg
split route did not fit even with them (1328). Pass the lookup tables, and cap the route with
Jupiter's `maxAccounts` when you quote. Measured 2026-09-29 with `@lazorkit/sdk-legacy` 1.2.0.

² Measured in April 2026 on protocol v1; not re-measured on v2.

Only a passkey Owner or Admin can call `Authorize` (TX1). TX2 can be submitted by any
signer — but if an inner instruction pays the TX1 payer or TX2's payer back, TX2 must come
from the `executor` named at TX1. See [Passkey signing](/web3js-v1/passkey-signing#deferred-execution-executor-and-feepayer).

## Revocation

Before expiry, a session can be revoked by an Owner or Admin:

```ts
// React Native
await revokeSession(
  { sessionPda, refundDestination: smartWalletPubkey! },
  { redirectUrl: 'myapp://cb' },
);
```

```ts
// React: the session it created, or a specific one (e.g. created with your own sessionKey)
await revokeSession();
await revokeSession({ sessionPda: 'SESSION_PDA_BASE58' });
```

`RevokeSession` closes the session PDA and refunds the rent, before or after expiry. Use
`refundDestination: smartWalletPubkey` (the vault, on mobile) to keep the rent in the
wallet.

After expiry, **anyone** may close the session with `CloseExpiredSession` (instruction
18, protocol v2) and keep the rent: the account authorises nothing any more. A session is
closable only once the slot is strictly past its expiry; before that the program refuses
with `SessionNotExpired` (3036). `@lazorkit/sdk` exports `createCloseExpiredSessionIx`;
`@lazorkit/sdk-legacy` 1.3.1 has no public builder for it.

## Costs

| Item                               | Cost            |
| ---------------------------------- | --------------- |
| Session account rent (one-time)    | 0.001448 SOL    |
| `CreateSession` tx fee             | 0.000005 SOL    |
| **Total setup**                    | **0.001453 SOL**|
| `Execute` via session (per tx)     | 0.000005 SOL    |

The rent comes back through `RevokeSession` — or, once the session has expired, to
whoever calls `CloseExpiredSession` first.

## Troubleshooting session errors

| Error                                   | Cause                                                                      |
| --------------------------------------- | -------------------------------------------------------------------------- |
| `0xbd0 ActionSolLimitExceeded`          | Lifetime SOL cap exhausted — revoke + recreate with a higher `solLimit`.    |
| `0xbd1 ActionSolRecurringLimitExceeded` | Window cap hit. Wait for reset or raise `solRecurringLimit`.                |
| `0xbc1 SessionExpired`                  | Session past its expiry slot — make a new one.                              |
| `0xbc0 InvalidSessionDuration`          | Expiry not in the future, or more than 6,480,000 slots ahead.               |
| `0xbcd ActionProgramNotWhitelisted`     | The call targets a program outside the whitelist — add it or drop the filter. |
| `0xbd6`–`0xbd8` (3030–3032)             | An inner instruction tried to reassign the vault or a vault token account's authority. |
| `0xbdc SessionNotExpired`               | `CloseExpiredSession` on a live session.                                    |

Full map in [Errors](/errors#program-error-codes).
