---
title: Protocol errors
description: Diagnose wallet, session, deferred execution and sponsorship errors on Protocol v1.
---

Use `extractErrorCode(error)` and `errorFromCode(code)` from the installed Protocol SDK
to decode the program's numbered errors. Check the transaction logs to identify the
program that reported the error. An invoked program can reuse the same numeric code.

| Code | Meaning | What to check |
| --- | --- | --- |
| 3002 | Permission denied | Confirm the authority belongs to the wallet and can perform the operation. |
| 3005 | Invalid message hash | Rebuild the approval for the intended instructions, accounts, cluster and deployment. |
| 3006 | Signature reused | Refresh the authority state and request a fresh passkey approval. |
| 3007 | Signature too old | Prepare the approval again with a fresh slot. |
| 3009 | Session expired | Register a fresh session and replace the stored session key. |
| 3014 | Deferred authorization expired | Prepare a new approval. The original payer can reclaim the expired record's rent. |
| 3015 | Deferred hash mismatch | Use the payload returned when the approval was created. |
| 3017 | Unauthorized reclaim | Sign with the payer recorded on the deferred account. |
| 3020–3032 | Session actions or account constraints | Review the session rules, asset balances and vault account ownership. |
| 4001–4007 | Protocol fee setup | Check the selected deployment's fee configuration, treasury and payer. |

For a paymaster error, inspect its response and check whether the request returned a
signature. When the outcome is unknown, query the original signature before retrying
the payment. See [Troubleshooting](/troubleshooting).
